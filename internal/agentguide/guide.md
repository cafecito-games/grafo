# Grafo structural code intelligence

Grafo maintains a deterministic semantic code graph for indexed repositories and
exposes it through the `grafo` MCP server and the `grafo` CLI. This text is
generated by `grafo install`; change Grafo's configuration rather than editing
it, because a reinstall replaces it.

## 1. Confirm the branch is indexed before trusting the graph

Grafo answers only from an index built for the current repository and branch.
Check once per session with `get_index_status` (CLI: `grafo status .`).

- No index for this repository or branch: say so, and use your native tools.
  Never present a graph answer as complete. `grafo index .` builds the index.
- Index present: prefer the graph for the structural questions below.

Grafo models code structure only. It does not model documentation, comments,
logs, generated output, dynamic runtime state, or anything outside an indexed
branch.

## 2. Route structural questions to the graph before content search

Use Grafo, not text or embedding search, for these questions:

| Question | Tool |
| --- | --- |
| Which symbol is this, and where is it defined? | `find_symbols`, then `get_node` |
| Show me its real source | `get_source` |
| Who calls it? What does it call? | `get_callers`, `get_callees` |
| How are these two symbols connected? | `find_path` |
| What else touches this symbol, config key, endpoint, event, or data store? | `get_neighbors` |
| Which HTTP endpoints exist, and who handles them? | `list_endpoints`, `find_handler` |
| Which outbound calls cross a service boundary? | `list_outbound_requests` |
| How do repositories communicate over HTTP and events? | `get_service_topology` |
| What breaks if I change this? | `get_blast_radius` |

Resolve a name to a node first, then pass the returned qualified name or stable
node ID to later calls instead of re-guessing text. External nodes are explicit
unresolved boundaries, not missing data. The symbol, node, source, caller,
callee, path, and impact tools accept a batch of inputs and return one result or
error per input, in order.

## 3. Before adding code, look for code to reuse

When you are about to write a new function, handler, or helper, call
`find_reusable_code` with a short description of the behaviour. It selects
candidates with embeddings and returns graph-resolved context for each, so
prefer extending a returned symbol over adding a near-duplicate. Say so
explicitly when nothing reusable exists.

## 4. Before a behaviour-changing edit, run bidirectional impact

Call `get_blast_radius` (CLI: `grafo impact <symbol>`) for every symbol whose
behaviour or signature you are about to change. The report is bidirectional:

- upstream: what depends on the symbol, so what your change can break;
- downstream: what the symbol depends on, so what constrains your change;
- impacted files, deduplicated per repository and path;
- cross-repository hops that federation resolved;
- config, data, and event relationships, each with the edge that proves it.

Each direction carries its own `truncated` flag. A truncated report is a partial
answer: raise the depth or limit, or narrow the root, before concluding that a
change is safe. State the impact findings before editing, not afterwards.

## 5. Fall back to native tools deliberately

Use your own search, read, and edit tools when the question is not structural,
the content is not code, the repository or branch has no index, or a Grafo tool
returns an error or an unresolved boundary. Name the fallback and the reason.
Never treat Grafo silence as proof that nothing references a symbol.
